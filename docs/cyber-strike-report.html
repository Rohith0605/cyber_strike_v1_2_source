01 / Project Overview

Abstract & Introduction

Abstract

Cyber Strike is a browser-playable two-dimensional space shooter developed using Flutter and Dart. The player controls a spacecraft in a scrolling space scene, automatically fires at incoming enemies, earns points by defeating targets, and advances through score-gated levels. The game includes four enemy classes, temporary weapon upgrades, a defensive shield, collision-based health loss, and keyboard and pointer movement.

The application uses Flutter widgets for its interface and a custom Canvas rendering layer for the animated battlefield. A periodic timer updates game state, while entity collections track enemies, projectiles, pickups, and particles. The project also demonstrates how source control and an automated web build can support publishing a playable browser version.

Introduction

Games combine continuous simulation with input handling, visual feedback, state transitions, and rules that are easy for a player to understand. Cyber Strike brings these elements together in a compact arcade project. Its science-fiction art direction uses a dark space palette with luminous cyan and magenta highlights to separate the player, hazards, projectiles, and rewards.

Flutter is generally associated with application interfaces, but its Canvas and CustomPainter APIs can also draw custom 2D scenes. Dart handles the game state, timing, collision checks, scoring, and controls. Targeting the web makes the project easy to share through a URL without asking visitors to install a native application.

Project identity

Cyber Strike is a single-player arcade shooter. The documented project does not include user accounts, a backend, or cloud-based score persistence.

Purpose of this report

This report explains the objectives, technologies, game systems, controls, architecture, local development steps, deployment workflow, and areas that should be tested before a formal demonstration.

Objectives & Technology Stack

2. Project Objectives

  • Develop a playable 2D space shooter using Flutter and Dart.
  • Render a dynamic scene containing a player ship, enemy units, bullets, pickups, particles, and a moving space background.
  • Manage timing, movement, collisions, scoring, health, and level changes through game-state logic.
  • Support keyboard movement and mouse/touch drag input.
  • Provide pause, restart, and game-over states for a complete basic play cycle.
  • Introduce progressive challenge through score thresholds and varied enemy types.
  • Create a reproducible workflow for building and hosting the web version.

03 / Product Scope

Features & Scope

Real-time arcade loop

Enemies descend through the playfield while the player moves and fires automatically.

Score and levels

Destroying enemies awards points. Score thresholds advance the player through four levels.

Multiple enemy types

Scout, Interceptor, Tank, and Phantom classes provide visual variety and different health values.

Temporary power-ups

Twin lasers, spread shot, overdrive fire, and shield pickups alter the current run.

Player controls

WASD or arrow keys move the ship; mouse or touch dragging offers an alternate input.

Game states

The interface supports starting, pausing, resuming, restarting, and game-over feedback.

Visual feedback

  • Glowing projectiles and coloured enemy silhouettes help distinguish objects.
  • Particles provide short visual effects when bullets hit or enemies are destroyed.
  • The ship can tilt with horizontal keyboard movement.
  • HUD elements show score, level, health, and temporary status notices.
  • Later levels change the background atmosphere and add asteroid decoration.

Scope boundaries

The current project is a single-player browser game. Cloud leaderboards, account management, online multiplayer, remote save data, and a backend service are outside the documented scope. They may be considered as future extensions rather than current capabilities.

Design principle

Visual effects should reinforce gameplay information. Enemy types, projectile trails, pickups, and HUD statuses use contrasting colours so important events remain easy to identify.

04 / Player Guide

Gameplay & Controls

Gameplay sequence

  1. Start a run from the opening overlay.
  2. Move the spacecraft to line up against approaching enemies and avoid direct collisions.
  3. Allow the weapon system to fire automatically while the game is running.
  4. Destroy enemy units to add their score values to the total.
  5. Collect falling power-ups by moving the ship into them.
  6. Reach score thresholds to enter later levels with additional enemy classes.
  7. Pause or resume as needed; restart after a game over to begin another run.

Control reference

Keyboard focus

Browser keyboard events may not be received if the game area does not have focus. Click inside the game area and try the controls again if movement does not respond. A practical release test should cover both keyboard and pointer input.

Health and survival

The player starts with three health points. According to the supplied game rules, health decreases only on direct enemy-to-ship collision, subject to a shield or damage grace period in the code. An enemy merely leaving the bottom of the playfield does not itself count as player damage.

06 / Pickups & Player State

Power-Ups

Power-ups appear as falling items in the playfield. The player collects an item by moving the ship into its pickup radius. Collection updates a temporary weapon tier or activates the shield, and the HUD displays a short status announcement.

Power-upEffectAvailability in current logic
Twin LasersFires two parallel projectiles per weapon cycle.Level 2 and above.
Spread ShotFires a three-projectile spread pattern.Level 3 and above.
Overdrive CannonFires a five-projectile pattern with a faster cooldown.Level 4 and above.
ShieldTemporarily protects the ship from collision damage.Available at all levels.

Temporary state

Weapon boosts have a timer. When the timer expires, the weapon returns to the base tier. The shield also uses a timer and can absorb a collision while active. These timers are tracked in the game state and updated during the main tick.

Player health

Health begins at three points. A direct enemy/ship collision can remove one health point unless the shield or post-hit grace period prevents it. When health reaches zero, the game stops the active run and switches to the game-over state.

Suggested tuning

  • Evaluate whether pickups spawn often enough to be useful without overwhelming the playfield.
  • Compare the duration and impact of each weapon tier during play tests.
  • Check that a shield is visually obvious to players.
  • Test collisions carefully to avoid unfair repeated health loss.

08 / Runtime Behaviour

Game Loop & State

Periodic update cycle

A periodic timer is initialized when the game screen is created. It calls the tick method at intervals of approximately 16 milliseconds. The tick exits while the run is inactive, paused, or the play area has no usable size; otherwise it updates the game state.

  1. Increment the frame counter and sample movement from held keyboard keys.
  2. Smooth the ship's visual tilt and update screen-shake or notification timers.
  3. Recalculate the current level from the latest score.
  4. Update weapon timers, shield timer, damage cooldown, and shooting cooldown.
  5. Fire projectiles automatically when the shooting cooldown permits.
  6. Spawn enemies and periodically spawn pickups.
  7. Advance bullets and enemies and remove projectiles outside the play area.
  8. Check projectile/enemy and enemy/player collisions.
  9. Move pickups and particles, collect valid pickups, and remove expired objects.
  10. Switch to game over when health reaches zero.

State variables

The game state includes score, level, health, player position, active entity lists, weapon tier and timer, shield timer, damage cooldown, pause/running/game-over flags, and visual-effect state. Restart resets the run-related values and clears active entities so a new run can begin.

Rendering

GamePainter receives the current entity lists and relevant visual state. It draws the background, stars, grid, projectiles, enemies, pickups, particles, shield, and player ship. Its repaint policy allows the scene to reflect the changing state on subsequent frames.

Timing note

A 16 ms timer interval is the requested update cadence, not a guarantee of a stable 60 frames per second. Browser throttling and device performance may change the effective rate.

09 / Rules & Validation

Collision & Health Logic

Projectile against enemy

The game compares the distance between the bullet centre and enemy centre with the sum of their collision radii. When the distance is inside the collision threshold and both objects are active, the bullet is marked for removal and the enemy loses one hit point. If enemy health reaches zero, the enemy is removed and the appropriate score is awarded.

distance(bullet, enemy) < bullet.radius + enemy.radius

Enemy against player ship

The player loses health only when the enemy position overlaps the ship within the configured collision radius and no protective rule blocks the damage. When a shield is active, it absorbs the collision. Otherwise, the damage cooldown ensures that collisions occurring close together do not continuously remove health during the brief protection interval.

direct enemy/ship contact
    ├─ shield active → absorb collision
    ├─ damage cooldown active → no extra health loss
    └─ otherwise → health decreases by one

Off-screen cleanup

Enemies that move beyond the lower playfield boundary are marked for removal. Leaving the screen is not treated as an impact on the player's ship and does not reduce health by itself. This keeps the health rule tied to direct ship contact.

Game-over transition

When health reaches zero, the code clamps health at zero, stops the running state, and marks the game as over. The player can then restart to initialize a new run.

Recommended validation

  • Confirm bullets reduce enemy health and score is awarded only when an enemy is defeated.
  • Confirm shielded collisions do not reduce health.
  • Confirm an enemy escaping below the playfield does not reduce health.
  • Confirm health cannot fall below zero and game over occurs at zero.
  • Test repeated collisions and verify the grace period feels fair.

Visual Design & Repository

12. UI and visual design

The game uses a dark navy background with cyan, magenta, violet, warm orange, and gold highlights. A translucent HUD separates the score and player state from the playfield while preserving visibility of the action. The spaceship and enemies are drawn from custom paths and shapes rather than raster sprite sheets.

Scene atmosphere

Layered gradients, star movement, subtle perspective grid, and later-level asteroids provide depth.

Combat feedback

Projectile trails, impact particles, enemy destruction bursts, and brief screen shake communicate events.

Object distinction

Different enemy colours, shapes, health bars, and pickup symbols help players identify threats and upgrades.

HUD and notices

Score, health, level, and status messages provide information about the current run.

11 / Developer Guide

Local Setup on Windows

Prerequisites

  • Flutter stable SDK installed and added to the Windows PATH.
  • Git installed for cloning the repository.
  • Visual Studio Code or another Dart/Flutter editor.
  • Google Chrome or another supported browser for web execution.

Step 1: Verify Flutter

Open PowerShell or the VS Code terminal and run:

flutter --version
flutter doctor

If Windows reports that flutter is not recognized, install the Flutter SDK and add its bin directory to PATH, then restart the terminal and verify again.

Step 2: Clone the repository

git clone https://github.com/Rohith0605/cyber_strike_v1_2_source.git
cd cyber_strike_v1_2_source

Step 3: Install dependencies

flutter pub get

Step 4: Run the game locally

flutter devices
flutter run -d chrome

Flutter should compile the application, open a browser, and print a local URL in the terminal. Use the published controls to check start, movement, pause, restart, scoring, collisions, and pickups.

Troubleshooting

  • Run flutter doctor -v for detailed SDK diagnostics.
  • Make sure the terminal is in the directory containing pubspec.yaml.
  • Rerun flutter pub get after dependency changes.
  • Inspect the browser developer console for web-specific errors.
Important

These commands are the procedure for local execution; this report does not claim they have been run on every target machine.

12 / Release Workflow

Build & Deployment

Build for the web

Flutter web output is a collection of static files, including HTML, JavaScript, assets, and loader files. GitHub Pages serves static web files, so the Dart project must be compiled before it can run in a browser.

flutter build web --release --base-href "/cyber_strike_v1_2_source/"

The output is generated in build/web. The repository-specific base path is important because the project is hosted at a subpath under the GitHub Pages domain.

Automated GitHub workflow

  1. Check out the source repository.
  2. Install the Flutter stable SDK in the hosted runner.
  3. Retrieve package dependencies using flutter pub get.
  4. Compile the release web application with the correct base path.
  5. Upload build/web as a Pages artifact.
  6. Deploy the artifact using the GitHub Pages deployment action.

Publishing configuration

In the repository's Settings → Pages panel, the source must be configured to use GitHub Actions for this workflow-based process. The Actions tab shows whether build and deployment jobs succeed or fail.

14 / Closing Section

Future Work & Conclusion

18. Future enhancements

  • Audio: add sound effects, music, and mute/volume controls.
  • Game depth: introduce boss encounters, additional stages, and unique objectives.
  • Persistence: add local high-score storage before considering online accounts or leaderboards.
  • Accessibility: improve contrast options, input flexibility, readable HUD text, and reduced-motion settings.
  • Mobile usability: refine touch controls and test different aspect ratios.
  • Testing: add unit, widget, and integration tests for state transitions, collisions, and controls.
  • Performance: profile update and paint costs, especially when enemy and particle counts rise.
  • Release confidence: add automated build checks and a repeatable browser smoke test.

19. Conclusion

Cyber Strike demonstrates how Flutter and Dart can support a browser-playable arcade game with custom 2D rendering, input handling, entity updates, collision detection, scoring, level progression, and temporary power-ups. Its visual identity and automatic deployment workflow make it a useful project for demonstrating both interface development and practical source-control practices.

Future work should prioritize reliable tests and a stable release process before adding larger gameplay systems. Separating confirmed behavior from unverified outcomes keeps the documentation useful for both development and academic review.
